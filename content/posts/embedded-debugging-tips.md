嵌入式调试和写业务代码最大的不同是：很多 bug 没法靠打印堆栈定位，甚至连"程序跑没跑起来"都得靠猜。整理几个常用但不高级的调试手段。

## 1. 一个 LED，抵得上半个调试器

在没有调试器接入、或者怀疑程序卡死/跑飞的时候，最简单的手段就是找个空闲 GPIO 接个 LED：

```c
void error_blink(int code) {
    for (int i = 0; i < code; i++) {
        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_LED);
        HAL_Delay(200);
        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_LED);
        HAL_Delay(200);
    }
    HAL_Delay(1000);
}
```

不同的错误码闪不同次数，肉眼就能大致判断程序跑到了哪个分支，哪怕板子在很远的地方也能看出个大概。

## 2. 串口打印永远是第一选择

只要还有一个空闲的 UART，`printf` 重定向到串口基本是性价比最高的调试方式：

```c
int _write(int file, char *ptr, int len) {
    HAL_UART_Transmit(&huart1, (uint8_t *)ptr, len, HAL_MAX_DELAY);
    return len;
}
```

小技巧：打印的时候带上时间戳（比如 `HAL_GetTick()`），排查时序问题会方便很多；批量打印时尽量避免在中断里直接 `printf`，容易拖慢中断响应，可以先丢进一个环形缓冲区，主循环里再统一输出。

## 3. 用一根杜邦线当"示波器"

没有示波器的时候，想知道某段代码执行了多久、某个中断触发了几次，可以在代码前后翻转一个 GPIO，再用万用表甚至肉眼观察 LED 亮度变化（频率快到一定程度，LED 会呈现出"变暗"而不是闪烁）：

```c
GPIOA->BSRR = GPIO_PIN_0;        // 拉高，代表开始
do_something_time_critical();
GPIOA->BSRR = (uint32_t)GPIO_PIN_0 << 16; // 拉低，代表结束
```

如果手头正好有示波器或逻辑分析仪，这一招会更精确：直接量出高电平持续时间，就是这段代码的执行耗时。

## 4. 怀疑硬件问题时，先怀疑供电和地

排查了半天软件逻辑发现没问题，很多时候根源其实是：

- 供电纹波太大，导致 MCU 或外设复位、通信异常
- 长导线 / 面包板接触不良
- 多个模块共地没做好，产生地环路干扰

一个简单的验证方法：把怀疑有问题的模块单独供电测试，或者在电源上并联一个电解电容加瓷片电容做滤波，看现象是否消失。

## 一点总结

高级调试工具（JTAG/SWD 调试器、逻辑分析仪、示波器）当然好用，但很多时候手头没有，或者问题出现在无法接调试器的现场环境。这时候一个 LED、一个空闲串口、一根杜邦线，配合清晰的逻辑思路，往往就能把问题范围快速收窄。工具是加分项，思路才是关键。
